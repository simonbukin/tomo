# Client independence

This document shows that a client that is not the Tauri and React app can
use Tomo. It also lists the parts that only the GUI implements today, and
what a second client must write again. Read it before you start a second
client, or before you move client logic into the daemon.

Tomo does not have a second GUI client, and this refactor does not make one.
The proof is a headless script and an import check. See PRD section 25.

## The proof

Two automated checks keep the claim true.

**`scripts/torture/client.sh`** runs in `scripts/torture/run-all.sh`. It
starts a scratch daemon with the fake agent, and runs
`scripts/torture/headless_client.py`. That script uses only the Unix socket
and the Python standard library. It does not use the CLI, Tauri, React, or
`tomo_rpc.py`. It keeps its own client state: it starts from the `subscribe`
snapshot and applies each event, as `app/src/store.ts` does. It asserts:

| Step | What it proves |
|---|---|
| `hello`, `subscribe` | A client gets protocol 3, the status, and a full snapshot. |
| `repo_add` | `repos_changed` and `worktrees_changed` show the repo and its main worktree. |
| `tab_create` | `tabs_changed` and `pane_changed` show a tab with one live pane. |
| `pane_split` | The tab layout becomes a horizontal split of the two panes. |
| `agent_spawn` | `agent_changed` shows the fake agent idle, with lifecycle authority and a session. |
| `pane_attach` | `pane_output` carries the terminal bytes of the agent. |
| `pane_send` | The agent waits, and `attention_added` opens a waiting item that needs a person. |
| `attention_view` | `attention_viewed` marks the item. A viewed waiting item no longer needs a person. |
| `checkpoint_create`, `checkpoint_resolve` | A checkpoint needs a person, and `attention_resolved` removes it. |
| `fs_list` | Each entry carries `modified_ms`; the daemon sends directories first, then names, without case. |
| `fs_recent` | Files from `git ls-files`, newest first, cut to `limit` (50 when absent). Each entry is a file, never a directory. |
| `attention_list` | The daemon list is the same as the client state. |
| `status` | The repo, worktree, pane, live pane, and agent counts are the same as the client state. |
| `pane_close`, `tab_close` | The pane, then the tab, its panes, and its agent leave the client state. |
| four times | The state from the live events is the same as a fresh snapshot on a second connection. |

The comparison covers repos, worktrees, tabs (title, position, layout, active
pane), panes (tab, worktree, live, kind), agents (kind, state, session), and
attention (kind, pane, viewed). A copy of the script that ignores
`tabs_changed` fails at the `tab_create` step.

**`app/src/clientModels.test.ts`** lists the pure client models. Each listed
module may import only another listed module or `app/src/generated/`. So a
listed module cannot import `react`, `@tauri-apps/*`, `store.ts`, or a
package. A planted `import type { State } from "./store"` in `order.ts`
made the check fail with `./order.ts imports ./store`.

## What is client-independent today

| Part | Where | Notes |
|---|---|---|
| Transport | `<data dir>/tomod.sock`, one JSON object per line | See "IPC" in [architecture.md](architecture.md). |
| Wire types | `Call`, `Event`, `CoreSnapshot`, `Snapshot` in `crates/tomo-proto/src/lib.rs` | The one source of truth. |
| TypeScript wire types | `app/src/generated/` | Generated by `ts-rs`. They import nothing. |
| Client 1: GUI | `app/src-tauri/src/lib.rs` | A Rust bridge that holds one socket, sends `hello` and each `invoke("rpc")`, and forwards frames. |
| Client 2: CLI | `crates/tomo-cli` | Uses the Rust types. See [cli.md](cli.md). |
| Client 3: harness | `scripts/torture/tomo_rpc.py` | A raw socket helper. |
| Client 4: proof | `scripts/torture/headless_client.py` | A full read and command loop with its own state. |
| Daemon rules | `tomod` | Worktree identity, layout validity, agent authority, attention creation and resolution, process ownership, recovery. |

`app/src/api.ts` is the only TypeScript module that talks to Tauri. It has
`rpc`, `startEventPump`, and the pane output routing. A second TypeScript
client replaces this one file with a socket or another transport.

### Pure client models

`app/src/clientModels.test.ts` keeps this list pure:

| Module | What a second client can use |
|---|---|
| `types.ts` | The wire types again, and the view types (`UiState`, `Filter`, `HomeOptions`). |
| `appearance.ts` | The defaults and the check of per-window view settings. |
| `order.ts` | Manual order and main worktrees first. |
| `activityModel.ts` | The "needs me" rule (`needsMeItem`, `needsMeItems`), `nowSignals`, activity merge. |
| `homeQuery.ts` | Worktree filter, search, sort, and group. |
| `layoutModel.ts` | Leaf ids, tab reorder, pane move preview, drop regions. |
| `uiState.ts` | `sanitizeUi`: the check of the saved UI state blob. |
| `shell/sidebarMode.ts` | Sidebar snap and window layout modes. |

Other modules are also pure at runtime, but they are not in the list:

- `notifyRoute.ts` imports the type `ToastLevel` from `store.ts`.
- `shell/bottomModel.ts` and `shell/daemonHealth.ts` import the type
  `DaemonHealth` from `store.ts`.
- `paletteModel.ts` imports the type `MenuItem` from `components/ui`.
- `glyphs.ts`, `previewModel.ts`, `keys.ts`, `links.ts`, and
  `settingsModel.ts` are presentation helpers for this GUI.

A type import disappears at runtime. But a TypeScript build that includes
the module also reads `store.ts`, and `store.ts` imports React. To add
`notifyRoute.ts` or `bottomModel.ts` to the list, move the one type into
`types.ts` first.

## What is still presentation-coupled

These parts live only in the GUI. A second client must write them again, or
live without them.

| Part | Where | What a second client does |
|---|---|---|
| Event fold | `applySnapshot` and `applyFrame` in `store.ts` | Start from `subscribe`, then apply each event. `tabs_changed` replaces the tabs of one worktree and drops the panes and agents that left its layouts. `headless_client.py` `fold` is a copy in about 40 lines. |
| "Needs me" | `needsMeItem` in `activityModel.ts` | Copy the rule. An unresolved item that is not `waiting` needs a person. A `waiting` item needs a person while it is not viewed and its agent still waits. `Store::activity_list` in the daemon has the same rule for `needs_me`. |
| Sort, filter, group | `homeQuery.ts`, `order.ts` | Copy them, or use the pure modules. The manual order lives in the UI state blob. |
| Signals | `nowSignals` (pure), `signalsFor` in `Signals.tsx` (store and addon slots) | Copy the priority order and the cap of three. Addon signals come from GUI addon slots. |
| Zoom | `State.zoomed` in `store.ts` | `pane_zoom` only sends a `zoom_request` event. The daemon does not keep zoom. |
| Focus | `focus_request` event, `State.focusRequest` | Each client decides what focus means. |
| UI state | `ui_state_get`, `ui_state_set`: one JSON value in the `kv` table | The daemon does not check it. `sanitizeUi` checks it on load. There is one blob for all clients. A second client must not write it, or it replaces the GUI view state. |
| Commands | `app/src/commands/*.ts`, `actions.ts`, addon `commands` | Palette names, shortcuts, and menus are not on the wire. A command there is one or more `Call`s plus UI steps. A second client makes its own list from `Call`, as the CLI does in its clap tree. |
| Notifications | `attention.ts`, `notifyRoute.ts`, `sounds.ts` | Each client decides how to announce an `attention_added` event. |
| Terminal rendering | `TerminalPane.tsx`, `terminals.ts` (xterm) | Decode `pane_output` (base64) into a terminal emulator. The daemon keeps one size for each PTY, so the last `pane_resize` sets it for all clients. |
| Browser panes | `app/src/browser/`, `app/src-tauri/src/browser.rs` | The daemon keeps the pane, its `kind`, and its `url`. The page is a Tauri child webview. Another client can show the url or open it outside Tomo. |
| Addon UI | `app/src/addons/` (React slots) | Addon data is on the wire: the addon fields of `Snapshot`, the addon events, and the addon calls. The views are not. This base ships no addons; see [addons.md](addons.md). |

## Why this coupling is acceptable

- **Reality stays in the daemon.** Everything that must survive a GUI
  restart, or that the CLI and hooks must see, is in `tomod`: repos,
  worktrees, tabs, layouts, panes, agents, attention, and processes. The
  proof reads and changes all of them without the GUI.
- **The coupled parts are opinions about display.** Sort order, signals,
  zoom, focus, toasts, and palette names can be different in each client.
  If the daemon owned them, it would need more calls and events, and each
  change of taste would change the protocol.
- **No second client exists.** PRD section 25 forbids a TUI and speculative
  client infrastructure. A move of this logic into the daemon now has a
  cost and no user.
- **The shared rules are pure and checked.** "Needs me", sort, and layout
  helpers are pure modules with unit tests. A second TypeScript client can
  import them. `clientModels.test.ts` keeps them free of React and Tauri.
- **The one duplicated rule has tests on both sides.** "Needs me" is in
  `store.rs` (`activity_list`) and in `activityModel.ts`.

## What a second client must do

1. Connect to `<data dir>/tomod.sock` (or `$TOMO_SOCKET`). Send `hello`
   with `protocol: 3`, then `subscribe`.
2. Keep the snapshot. Apply each event as `applyFrame` in `store.ts` does.
   Ignore an event that you do not know.
3. Send `pane_attach` for each pane that you show, and decode
   `pane_output`. Send `pane_detach` when you stop.
4. Run commands as `Call`s. Use the result, but let the events change your
   state.
5. Copy "needs me" from `activityModel.ts`, or import it.
6. Choose your own sort, signals, zoom, focus, notifications, and commands.
7. Do not write `ui_state`. It belongs to the GUI.

## Problems found (not fixed)

- `attention_next` returns the first unviewed item. The GUI and the "needs
  me" rule skip a waiting item whose agent no longer waits, and keep a
  viewed checkpoint or crash. So `tomo attention next` and the GUI can pick
  different items.
- `ToastLevel` and `DaemonHealth` are in `store.ts`. That keeps
  `notifyRoute.ts`, `shell/bottomModel.ts`, and `shell/daemonHealth.ts` out
  of the pure list.
- `ui_state` is one blob for all clients (see above).
